### [MAJOR][CONFIRMED] S1 — Unauthenticated, unrated spectator attach is a CPU + egress amplifier. There is no connection cap and no rate limit outside `match:action`.

`packages/server/src/index.ts`

The token bucket exists and is real (`#spend`, `index.ts:730-740`), but it is called from
exactly one place: `#dispatch` (`index.ts:703`). Every other message — `lobby:list`,
`lobby:create`, `lobby:join`, `lobby:spectate`, `match:spectate`, `match:sync`,
`session:resume` — is free, and none of them requires a session. `#requireSession` is
only on `lobby:leave`/`lobby:ready`/`lobby:start`/`match:sync`/`match:action`.

`WebSocketServer` is constructed with `noServer: true, maxPayload: MAX_PAYLOAD_BYTES`
(`index.ts:135-142`) — there is **no `maxConnections`**, no per-IP limit, and `#conns` is
an unbounded `Map`. So a socket is free and unlimited.

**The amplification chain, all of it unauthenticated:**

1. `lobby:list` → every **public** lobby's `lobbyId` (`lobby.ts:189-196` filters private
   ones for a `null` viewer, correctly).
2. `lobby:spectate` with that `lobbyId` → `#joinLobby(..., asSpectator=true)`
   (`index.ts:359-360`, `404-417`) sends `lobby:state` built by `lobbyView`, whose
   `Lobby.matchId` field carries the running match's id (`protocol.ts:223`).
3. `match:spectate` with that `matchId` → `#spectate` (`index.ts:655-668`) mints a session
   and `#attach`es the socket to `room.onBroadcast`'s watcher set. **No credential, no
   membership, no check that the caller was ever in the room.**
4. Now every committed action runs `#watchRoom`'s callback (`index.ts:744-767`), which for
   **each** watcher calls `#sendMatchState` → `room.viewFor(...)` → a fresh
   `playerView` + `playableConspiraciesFor` + `openQuestionFor`, then
   `JSON.stringify`s the whole `ClientState` (~60 KB per `index.ts:683`'s own estimate)
   and writes it to that socket.

`Room.dispatch` is documented as synchronous end to end and the process is single-threaded
(`room.ts:24-28`). So K spectators cost K full projections **inside the action handler**,
and a real player's answer blocks on all of them. K = 10,000 gives ~600 MB of egress and
10,000 `JSON.stringify` calls per action, from one `match:spectate` frame per socket.

The docstring at `index.ts:610-613` says the design is safe because "Spectators cannot
dispatch, full stop — there is no flag to forget to check". That is true and it is not the
problem: the problem is the *read* side, which is unbounded.

Also unbounded, and cheaper to abuse: `lobby:create` is unauthenticated and unrated, so
anyone can allocate `LobbyHub` entries and `SessionRecord`s without limit; and
`match:sync` needs only a spectator session to pull another full 60 KB state on demand,
in a loop, with no budget.

**Repro (no tools beyond a socket):**
```
ws -> {"t":"lobby:list"}
ws -> {"t":"lobby:spectate","lobbyId":"<any public lobby>"}   // reply carries matchId
ws -> {"t":"match:spectate","matchId":"<that id>"}            // attached, full state
// repeat the last frame on K sockets, then have one player press ANSWER.
```

**Fix, cheapest first.** (a) Put `#spend` in front of every message, not just
`match:action`. (b) `maxConnections` on the `WebSocketServer` and a cap on
`#watchers.get(matchId).size`. (c) Give spectator sessions the same token-bucket as
players, so a spectator is at most a few states per second rather than one per action.
(d) Consider not re-sending a full state to a spectator whose `viewId` it already has,
which would fix the fan-out rather than the rate.

Confidence: CONFIRMED for every step in the chain (all read from source; the steps are
plain field reads). NOT measured — I did not stand up a server and drive 10,000 sockets,
so I am not claiming a throughput number.

### [MAJOR][CONFIRMED] C1 — KHAKI TERROR's lock is cleared by ANY resource loss, not by a donation.

`packages/engine/src/reduce.ts:898-917` (`creditDonation`), called from the `lose` case
at `reduce.ts:1128-1140`.

`creditDonation` has no idea which card drained the player:

```ts
function creditDonation(state, id, taken) {
  const given = deltaTotal(taken);            // a TOTAL, not a per-type vector
  ...  const next = Math.max(0, r.remaining - given);   // for ANY 'no-purchases' entry
```

**Reproduction (probe run under `tsx` against the real engine and the real corpus; probe
file kept out of the repo, in `%TEMP%\opencode`).**

Setup: two seats. `p1` holds 9 Funds and nothing else, and holds KHAKI TERROR
(`packages/cards/scripts/playable.ts:118`, the shipped reduction
`[{op:'lose', res:{funds:1,clout:1,media:1,trust:1}}, {op:'restrict', kind:'no-purchases', owed:4, until:'rest-of-game'}]`).
`p2` holds a probe card `[{op:'lose', res:{funds:4}, target:'each-opponent'}]` — an
unrelated drain, with no donation clause at all.

```
after KH              : {"funds":8,...} | no-purchases remaining=4
after unrelated drain : {"funds":4,...} | (no restrictions at all)
purchasesBlocked      : false
```

`p1` lost 4 Funds to somebody else's card, donated nothing to the Public Reserve, and the
purchase lock vanished — the entry was not merely zeroed, it was removed by
`creditDonation`'s `filter`.

Three separate divergences, all CONFIRMED:

1. **Wrong condition.** The lock's condition is "until you donate". The implemented
   condition is "until some card costs you resources". A drain is not a donation.
2. **Wrong shape.** The printed card says "Donate 1 resource of **each type**" — a
   four-element requirement. `Restriction.remaining` is a single scalar decremented by
   `deltaTotal(taken)`, so 4 Funds of one type satisfies "one of each of the four". The
   `Delta` that `taken` actually is carries the per-type information; it is summed away
   before it is compared.
3. **The card's own donation does not count against its own lock.** `applyEffects` runs
   the effect list in order, so `lose` (and its `creditDonation`) executes *before*
   `restrict` writes the entry. The probe shows `remaining=4` immediately after the card
   resolves, even though the card just took its own 1-of-each. A player who plays
   KHAKI TERROR and pays the whole ask in the same breath is still locked to 4.

**Why this is the interesting kind of bug for this codebase.** `state.ts:809-836`
devotes a careful argument to *why* decrementing by the ask rather than by the take would
be a soft-lock — and gets that right. It never asks the other question: whether an
opponent's drain should count as the caster's donation. The argument is sound about its
own subject and silent about a neighbour, which is exactly the shape the `reducer-parity`
honesty tests are meant to catch and do not: the card is fully executable, the op is in
the registry, the schema accepts it. Nothing in the corpus pipeline compares a card's
*text* with the *semantics* of its reduction.

**Fix (smallest honest version).** Gate `creditDonation` on the loss actually being the
donation — thread a donation flag through the effect, so only the KHAKI TERROR clause
decrements `remaining` — and compare a per-resource vector against a per-resource
requirement rather than a scalar total. If the intent really is "any loss counts", the
printed text has to change, and `packages/cards` owns that.

### [MAJOR][CONFIRMED] T3 — The `ZoneSelector` axis is absent from the G21 satisfiability proof, whose docstring claims a full cross-product.

`packages/engine/test/choices.test.ts:511-533` enumerates the axes that can move a ceiling
between the raise and the answer, and lists five: chooser pool, other pools, peg layout,
count, scope. `ZoneSelector` is a sixth and it is not in the loop.

`probeEffect` (`choices.test.ts:651-657`) is the only place the probe effects are built,
and the only one carrying a `zone` is the `choose-zone` probe:

```ts
if (kind === 'choose-zone') {
  return { op: 'discard-voter', n: count, target: 'each-opponent', zone: 'chosen-zone' };
}
return { op: opFor(kind), n: count, target: 'each-opponent' };   // no `zone`
```

So across the whole exhaustive sweep, **`evict-voter`, `discard-voter` and
`convert-voter` are never raised with `'this-zone'`, `'your-strongest'` or
`'chosen-zone'`**, and `choose-zone` is only ever exercised on a `discard-voter` op.

That matters because `zone` is precisely a narrowing that can produce an empty target set.
`resolveZone` (`reduce.ts:965-993`) returns `null` when it cannot resolve, which
`targetableCount` (`reduce.ts:3000-3023`) then reads as "the whole board" — the safe
direction — but a *resolved* zone is a real narrowing, and `resolveChoice`'s
`if (c.zoneId !== undefined && area.zone !== c.zoneId) return fail('that voter is in
another zone')` (`reduce.ts:2905`) is the only thing keeping the pick set equal to the
offered set. Untested combinations include `convert-voter` + `'chosen-zone'` (two
narrowings stacked: which zone, then whose voter) and `evict` + `'your-strongest'`.

I traced each of those by hand and I believe they are satisfiable — `wanted` is
`Math.min(c.count, targetableCount(...))` and the pick space is enumerated over exactly the
pegged areas, so an empty narrowing yields `wanted = 0` and an empty pick resolves. So
this is a **gap in the proof, not a defect I could demonstrate**, and the distinction is
the one the brief asks for.

Same family: `pegged()` (`choices.test.ts:396-409`) takes pegs from a flat
`zones.flatMap(...)` list, so with `own + foreign + volatile <= 4` every peg lands in the
first zone. The sweep never exercises a multi-zone peg layout, so `choose-zone`'s "pick
the one zone with a legal peg" is never asked to discriminate between two populated zones.

Closing it is three lines: a fourth dimension in `probeEffect`, driven from a
`ZoneSelector[]`.

### [MINOR][SUSPECTED] S2 — `order` is a **per-card** bit derived from `_seed`, and `_seed` determines the whole Ideology draw order.

> #### ⚠ CORRECTION, 2026-10-04. This finding was published as **[MAJOR]** and it was
> **wrong about the shape of the leak**, and wrong in the direction that matters: it
> **over-claimed**. The text it published — *"The answering player receives `order` on every
> card they answer: one bit of avalanche output per turn about a 32-bit value. Thirty-two
> answers is thirty-two bits."* — is false, and the mitigation it proposed would have made
> the real problem worse. Both halves are corrected below and the reasoning is recorded
> rather than deleted, because an audit that quietly drops a wrong finding is not an audit.
> Severity is downgraded **[MAJOR] → [MINOR]**; `SUSPECTED` is unchanged. **What survives is
> a real dependency between two secrets. What did not survive is the magnitude, which was
> the entire force of the MAJOR label.**

`packages/server/src/broadcast.ts:709-722` (`orderFor`) folds the match's PRNG **cursor**
into a hash of the card id and returns one bit:

```ts
const seed = state._seed;
... avalanche ...
return ((h >>> 16) & 1) === 0 ? 'ab' : 'ba';
```

The inputs are `_seed` and the **card id**, and nothing else. No turn number, no seat, no
answer counter.

#### Why the published bit-count was wrong: `_seed` is a cursor that does not move per answer

`orderFor`'s only seed input is `state._seed`, and `GameState._seed` advances on **a deck
reshuffle and on nothing else** — `draw()` is its only writer in `reduce.ts` (`:200-201`),
and it writes there only when a pile empties and the discard is re-shuffled. `ANSWER` does
not touch it. `INFLUENCE` does not touch it. `END_TURN` does not touch it.

So the bit is a **per-card constant for the life of the match**: turn 1 and turn 400 showing
the same Ideology Card show the same `order`. Consecutive answers therefore do **not**
produce independent bits, which is precisely the premise the published text rested on. The
oracle is **one bit per distinct Ideology Card ever dealt**, and a card that recycles
through `draw()`'s reshuffle contributes **no fresh information at all** about the cursor,
because the bit it hands over is the bit it handed over last time.

This is now the pinned, engine-half property rather than my reading of it:
`packages/engine/test/rng.test.ts`'s *"the order is a per-card constant: `_seed` moves on a
reshuffle and on NOTHING else"* block asserts `ANSWER` leaves the cursor where it was,
asserts `INFLUENCE` and `END_TURN` do too, and — the non-vacuity half — asserts a reshuffle
**does** move it.

#### The characterisation of `state.ts` was also wrong

As published, this finding cited `state.ts:1014-1016` as asserting *"the Ideology draw order
is seed-derived"*. That is not what is there now, and it was not the load-bearing text even
when it was. The assertion that matters is on **`GameState._seed`, `state.ts:1353-1364`**,
and it says the opposite of what S2 assumed:

> **IT ADVANCES ON A RESHUFFLE AND ON NOTHING ELSE** … That is load-bearing for one thing
> above everything else in this file: the server derives a card's two-faces presentation
> order from `_seed` and the card id, so **the order is a per-card constant for the life of
> the match**, not a per-answer draw.

The file header (`state.ts:21-44`) carries the ruling in its own heading — *"THE ORDER IS A
**PER-CARD** CONSTANT, and this line used to say 'answer ORDER'"* — and names this very
finding as the thing it corrects.

#### What survives, and it is still a finding

`_seed` is listed in `playerView.ts:20-23` and on `GameState._seed` as the thing whose loss
matters, and the dependency is real in the direction that does not depend on my bit-count:
`setup.ts:98-113` shuffles every deck from the seed, threading it forward, so recovering
the seed recovers the entire initial order of every deck — which is what `playerView`'s
header calls THE DECKS, the first thing it says it protects. `FULL-INFORMATION.md` §3 calls
`order` the only thing being withheld. So there is still a dependency between two secrets
that `FULL-INFORMATION.md`, `playerView.ts` and `secret-inventory.ts` do not state between
them. It is one bit per distinct card dealt to the answering seat, not one bit per turn.

**Why SUSPECTED rather than CONFIRMED.** Unchanged, and the reason is still real:
`orderFor`'s constants live in the server source, which a network attacker does not have, so
"observe the bits and invert the avalanche" is not a wire-only attack. It becomes one the
moment the construction is disclosed — a fork, a client that reimplements the order, a source
leak, a write-up.

#### The proposed mitigations, adjudicated

- **REJECTED — *"rotate a dedicated order-salt in state each answer so consecutive answers
  are independent."*** This is the mitigation that would have made it worse, and it is
  rejected on two independent grounds. **(a) It contradicts the shipped design records.**
  `PLAN.md` row 18 is *"Seeded **per-card** answer ordering"*, `PLAN.md` §2's status note
  calls `orderFor` *"a derived **per-card** field, a pure function of the match seed and the
  card id"*, and `docs/UI-SPEC.md` §1.2 is *"Randomise the presentation order **per card**"*.
  A per-answer salt makes `order` a function of the salt's history, so the same card can
  arrive either way — which breaks `broadcast.ts`'s reconnect-stability reasoning (*"a
  redraw changes the card and therefore the order, which is correct: it is a different
  question"*, a claim that is only true if the card is the whole input) and breaks the
  property `secret-state.test.ts` pins as *"a different match seed gives a different order
  for the same card"*. **(b) It enlarges the leak.** Per-card leaks **less**: a recycled card
  hands back the bit it already handed back. A per-answer salt publishes a **fresh** bit
  every turn, forever — which is the very oracle this finding claimed to exist and did not.
  Taking the mitigation would have converted a finding into a defect.
- **REJECTED — *"derive the order from a value that is already public (`turn`, the seat
  index, the card id alone) rather than from the cursor."*** `broadcast.ts:641-667` records
  why, and it is not a preference: the pending card's id is withheld as a *field* but is
  recoverable by *content* (the corpus is public JSON in this repository), so a
  public-value derivation lets every client compute `order` and rebuilds the
  position-to-Ideologue lookup that amendment A′ exists to withhold, in one line.
- **STILL OPEN — *"fold in a secret that is not the PRNG cursor."*** This is the only one of
  the three that survives, and `broadcast.ts:669-686` already narrows it: every mitigation
  that removes the seed fold publishes A′, so the fix is a **second, independent secret with
  more entropy than the table can publish** — a second `_`-prefixed salt in `GameState`,
  minted by `setup` beside the seed. That is an engine change (`GameState`, `setup`,
  `ServerOnlyKeys`, `SECRET_FIELDS`) and is deliberately not half-built in the server
  package. **Open, not closed by this correction.**

### [MAJOR][CONFIRMED] T4 — Seed-coupled pins in `winnable.test.ts`: the ending turn and the final scoreboard of one seeded game are asserted exactly.

`packages/engine/test/winnable.test.ts:194,202-206,215`

```
expect(s).toEqual({ p1: 0, p2: 28, p3: 5, p4: 15, p5: 21 });      // :194
const decided = {
  2: { seed: 1, turn: 50, majorities: 9 },
  3: { seed: 1, turn: 58, majorities: 9 },
  4: { seed: 1, turn: 65, majorities: 9 },
  5: { seed: 19, turn: 72, majorities: 9 },
};
...
expect(state.turn, `${n} players ended on an unexpected turn`).toBe(pin.turn);   // :215
```

The suite's stated claim at `:198` is "2-, 3-, 4- and 5 players all reach a **decided
board**". `majorities === 9` is that claim. `turn === 58` is not: the exact turn a game
ends on is a function of (a) every Ideology, Voter, Headline and Conspiracy payout in the
corpus, and (b) the *driver policy* inside `playFullGame`, which exists only to make games
finish and is not a rule. Change one card's `pays` by one resource, or change one line of
the driver, and this test goes red with a message that names neither the card nor the
cause. Same for the scoreboard at `:194`.

Note the contrast **inside the same file**, which is what makes this a defect rather than a
house style. The regression this suite exists for is asserted at `:185` as

```ts
expect(state.turn).toBeGreaterThan(SHIPPED_IDEOLOGY);
```

— the property that actually matters, stated as an inequality against a quantity that means
something. The exact-equality `turn` pins four lines later are debugging residue promoted
to assertions.

**Why a wrong-reason pass here is more corrosive than a missing test.** A test that is
*too weak* says nothing and can be added later. A test that pins the wrong constant does
two harmful things at once: it reports a real engine change as a failure (so the next
person "fixes" it by updating the constant, which is exactly how a regression would be
absorbed), and it makes a corpus edit look like an engine bug. `packages/cards` owns card
content; this suite is in `packages/engine` and cannot tell the difference.

**Fix.** Delete `pin.turn` and the `scores` literal. Keep `majorities`, keep
`toBeGreaterThan(SHIPPED_IDEOLOGY)` for the 5-seat case, and — if the exact turn is worth
remembering — assert it with an explicit comment saying it is a *witness*, not a
specification, e.g. `expect(state.turn).toBeGreaterThan(pin.turn - 5)`.

## Severity 4 — Test quality (wrong-reason passes)

Covered above as T1-T5; this section states the pattern.

### The pattern, and why it outranks a missing test

Four findings in this audit (T1, T2, T4, T5) share one shape: **a guard that is asserted
to exist, and does not, or that exists and pins a number which no longer means anything.**
They are grouped here because the grouping is the finding. A missing test is a debt with
an obvious shape; a wrong-reason pass is a debt that actively misleads, because it
converts the next real defect into "the pin is stale, update the pin".

Ranked by how much damage each does to the next person:

| id | what the guard claims | what is actually there | damage |
|---|---|---|---|
| T1 | `derive.ts:65-67`: "`derive.test.ts` imports the real `RULES` and asserts equality" — the stated reason 18 UI constants are trustworthy | no such file, and `derive.ts:21-26` says so in the same document | a client/engine numeric divergence is invisible; the comment actively discourages anyone from adding the guard |
| T4 | `winnable.test.ts:215`: four exact ending turns, `:194`: an exact five-seat scoreboard | a corpus-and-driver fingerprint | a card edit is reported as an engine failure; a real regression can be "fixed" by editing the pin |
| T2 | `interrupt.test.ts:339-374`: the `describeEffect` block | 5 of 16 ops covered, `restrict` not among them | green suite over a function whose contract is "never paraphrase a card into a lie", and whose one wrong arm is the untested one |
| T5 | `derive.ts:17-34`: the client mirrors five engine rules by hand and cannot import the engine | true, candidly documented, compensated by 1480 lines of `choiceResolver.test.tsx` | low — this one is honest about itself |

### The two structural holes underneath them

1. **`reducer-parity.test.ts` proves EXECUTABILITY, not SEMANTICS.** It correctly
   re-derives the op set, the per-op read fields, the trigger raise sites and the target
   switch from `reduce.ts`'s own source text, in both directions, with non-vacuity
   assertions. What no test in the repo can see is whether the *semantics* of a reduction
   match the *sentence on the card*. C1 is a fully-executable, schema-valid, registry-
   valid KHAKI TERROR whose printed text and behaviour disagree in three ways, and it
   ships green through the strongest honesty suite in the project. That is not a bug in
   the suite; it is the boundary of what source-text derivation can reach.
2. **`choices.test.ts`'s G21 proof is exhaustive over the axes it lists and silent about
   one it does not** (T3). The docstring is careful to say the *reactive* sweep skips
   cases it cannot probe, and the constructive block exists precisely to fix that. The
   remaining gap is a single missing dimension (`ZoneSelector`), found by asking what else
   `raiseVoterDecision` reads.
